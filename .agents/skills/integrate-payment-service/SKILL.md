# Integrating with the Payment Service

The Payment Service exposes robust APIs to generate payment gateway orders and securely process webhooks. This document outlines how other microservices in the food delivery ecosystem should interact with it.

## 1. Creating a Payment Order

When a user initiates checkout, the upstream service (e.g., Order Service) must request the Payment Service to create an order *before* showing the payment UI to the client. This tightly couples the cart amount to the gateway to prevent client-side price tampering.

**Internal Flow:**
The service uses the `PaymentGatewayOrchestrator#createOrder(String gatewayName, PaymentRequestContext context)` method. 

**Required Context Parameters:**
- `internalOrderId` (UUID): Your service's internal representation of the cart/order.
- `amountInInr` (BigDecimal): The exact total checkout amount. No floating-point math should be used.
- `receiptRef` (String): A receipt identifier (mainly for Razorpay).
- `customerPhone` (String): The user's phone number (required by Cashfree).

**Response:**
Returns the specific `gatewayOrderId` (e.g., `order_XyZ123`). The frontend client application uses this ID to initialize the Razorpay or Cashfree SDK.

## 2. Webhook Ingestion (For Reference)

Other services do not call webhooks directly. The payment gateways call these endpoints:
- `POST /api/v1/webhooks/razorpay`
- `POST /api/v1/webhooks/cashfree`

These endpoints verify the cryptographic signatures and offload the event to `WebhookProcessingService`.

## 3. Listening for Payment Success

Since the Payment Service asynchronously receives webhooks (e.g., `order.paid` or `payment.captured`), downstream services must wait for the Payment Service to broadcast this success. 

**Integration Pattern:**
- Do not poll the Payment Service database.
- Future implementations of this service will publish a message to a message broker (e.g., Kafka or Pub/Sub) when `WebhookProcessingService` transitions an order status to `COMPLETED`. 
- Other services (e.g., Kitchen Dispatch, Delivery Fleet Service) should subscribe to these events to fulfill the order.

## 4. Idempotency Requirements

If you build an internal REST API endpoint in this service that is callable by other microservices, you *must* pass the `Idempotency-Key` HTTP header. 
- The key should be a unique UUID generated by the calling service.
- It prevents network retries from accidentally double-charging the user.

## Example: Using the SDK in a Frontend Client
Once the backend returns the `gatewayOrderId`, the frontend (Web/Android/iOS) initializes the respective gateway's SDK. The frontend *must not* be trusted to confirm payment success. Always rely on the backend webhook to trigger fulfillment.
